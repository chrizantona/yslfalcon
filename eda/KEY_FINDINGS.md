# EDA: ключевые выводы и правила разработки

Источник всех цифр — `eda/eda.ipynb` (исходник `eda/eda.py`). Прежде чем менять загрузку данных, валидацию, обучение или сабмит, сверься с этим файлом.

## 1. Задача
- Open-set ReID автомобилей: для каждого снимка из `test_query.csv` упорядочить снимки из `test_gallery.csv` по убыванию сходства и сдать top-10.
- Метрика качества (45% оценки) — **mAP@10 по `submission.csv`** (ответы организаторов от 16.09.2026): совпадения «та же машина + та же камера» выкидываются до усечения до 10 позиций, AP делится на min(n_pos, 10), усреднение по запросам; запросы без верного ответа исключаются. Rank-1 и Rank-5 — дополнительные столбцы. Полный mAP и mINP по `embeddings.npy` публикуются справочно, в баллы не входят.
- Режим отказа (10%): баллы = 10% × (0,7·F1 + 0,3·TNR), считаются только по `candidates.csv`, на уровне запроса, по верхнему кандидату (TP — пара есть и верхний верный; FP — ответили неверно или пары нет; FN — пара есть, отказ; TN — пары нет, отказ), F1 — micro. В закрытом тесте **20% запросов без пары**, они не помечены. Порог обосновывается на защите.
- Производительность (20%): 10% × балл времени + 10% × балл FPS. Время на одно ТС — полный цикл от чтения файла до L2-нормализации, медиана 300 прогонов после 50: ≤ 40 мс — полный балл, 40–80 мс — линейно, > 80 мс — 0. FPS — лучший из батчей 1 / 8 / 16 / 32, не меньше 10 с на каждый: ≥ 100 — полный балл, 50–100 — линейно. Поиск по галерее и re-ranking в замер не входят. Стенд: RTX A5000 24 ГБ, 2× Xeon Gold 6338 (2,0 ГГц), CUDA 12.2, GPU в Docker через `--gpus all`. Фиксируются также пиковый VRAM, время загрузки весов, детерминизм. Суммарный размер всех весов инференса > 2 ГБ — решение не допускается к оценке производительности.
- Протокол **потоковый**: каждый запрос обрабатывается независимо, доступна вся галерея. Query expansion и кластеризация по запросам запрещены; re-ranking внутри топ-K одного запроса по галерее и TTA одного снимка разрешены. Лимит на весь прогон ≈ время на ТС × размер теста × 3 (около 4 минут).
- Инференс офлайн, в Docker, запуск одной командой; при `docker build` сеть разрешена, при запуске — нет. Версии пакетов закрепить точно, веса — в образе или скачиваются в Dockerfile с проверкой sha256.
- Детекция, распознавание номеров и трекинг не нужны: рамки даны.

### Формат сдачи (README датасета)
- `submission.csv`: `query_id, gallery_id_1, …, gallery_id_10`.
- `embeddings.npy`: сначала все `image_id` из `test_query.csv` в порядке файла, затем все из `test_gallery.csv`.
- `candidates.csv`: `query_id,gallery_id,confidence`, заголовок обязателен; отказ — **отсутствие строк** для запроса; `confidence` — любая монотонная шкала; кандидатов можно несколько, в расчёт идёт верхний.
- `submission.csv` содержит 10 кандидатов для каждого запроса, в том числе отказанных. `embeddings.npy` — float32, (1110 + 750, D), нормализация на стороне организаторов.

## 2. Данные — факты

| Что | Значение |

| train | 9556 снимков, 1541 машина, 96 камер |
| test | query 1110, gallery 750, ≈ 300 машин |

| снимков на машину | 4–8, медиана 6 |
| камер на машину | всегда ≥ 2, у 67% машин ровно 2 |

| дисбаланс камер | камеры 89 и 90: 21% снимков и 301 общая машина; у 15 камер меньше 20 снимков |
| рамки | медиана ≈ 670×490 px, w/h ≈ 1,35; 8,5–10% обрезаны краем кадра |

| ракурс | 48% снимков — вид сзади; у 46,5% машин одна камера видит перед, другая — зад |
| такси и каршеринг | такси 4–6%, плюс однотипные машины каршеринга с одинаковой ливреей |

- В `train.csv` есть колонка `camera_id`, в `test_*.csv` её нет. Организаторы подтвердили: колонка добавлена намеренно, для PK-сэмплинга и кросс-камерной валидации с тем же junk-протоколом; подавать её или производные признаки в модель нельзя.
- Один кадр — одно ТС; `image_id` уникален в каждом файле (формулировка ТЗ про несколько ТС на кадре — ошибка).
- Train и test из одного распределения: adversarial AUC 0,52–0,57. Камеры в тесте те же (по фону 92 из 96), машины новые.
- Пересечения машин между train и test нет: сходство test → ближайший train распределено так же, как train → ближайшая чужая машина.
- 11 кадров лежат дважды под разными `image_id` с разными рамками (две машины в одном кадре): 9 пар train↔train, 1 train↔gallery, 1 query↔gallery.

## 3. Как собран тест (раздел 7 ноутбука)
- **gallery = один случайный кадр на каждую пару «машина + камера»; query = все остальные кадры.** Псевдо-тест, собранный так из train, совпадает с реальным тестом по всем проверкам: отношение query/gallery 1,44–1,49 против 1,48, доля запросов с почти той же рамкой в gallery 75–76% против 74%, соседние строки gallery никогда не из одной серии.
- Следствия:
  - почти у каждого запроса в gallery есть кадр из той же серии (та же камера): модель ставит его первым, но метрика его выбрасывает;
  - засчитываются только кадры той же машины с других камер, у 2/3 машин такой кадр ровно один;
  - в публичном тесте у каждого запроса есть совпадение, поэтому TNR на нём не измерить; в закрытом тесте 20% запросов без пары.
- **Закрытый тест собран иначе (ответ организаторов 20.10.2026):** кадров машины запроса с камеры запроса в его gallery нет — при сборке стояли фильтры на пересечение камер. Верным может быть только кадр с другой камеры, z-оценка верного ответа ниже, и порог отказа калибруется на gallery без этих кадров (постановка `clean` из EXP-209).
- **CSV теста отсортированы по машинам:** у 84% запросов ближайший снимок gallery лежит в пределах ±10 строк от строки i × 750/1110. Это утечка, её не используем.

## 4. Как делать

### Валидация
1. Делить train **только по `vehicle_id`** (GroupKFold, ~300 машин в фолде). Деление по снимкам запрещено: кадры одной серии утекают между фолдами.
2. В отложенной части собирать псевдо-тест функцией `make_pseudo_test` (раздел 7 ниже) и **перемешивать строки** перед инференсом.
3. Считать метрики функцией `evaluate_fold` (`src/reid/evaluate.py`, протокол `val_v2`): главная — mAP@10 по топ-10, как у организаторов; пары «та же машина + та же камера» выбрасываются, остальные кадры той же камеры остаются негативами; полный mAP и mINP — справочно. Эталонный `evaluate.py` организаторов опубликован рядом с архивом датасета — когда он будет у нас, сверить с ним и перейти на него.
4. Порог отказа калибровать на псевдо-тесте с искусственными отказными запросами: убрать из gallery машины так, чтобы около 20% запросов остались без пары. Выбирать порог по максимуму 0,7·F1 + 0,3·TNR с официальным подсчётом на уровне запроса и перенастраивать после каждой смены модели.
5. Уверенность для отказа — **нормированный score**: z-score top-1 относительно всех сходств запроса с галереей или отрыв top-1 от top-2. Re-ranking — только потоковый, без других запросов. Сырой косинус не годится: у готовых моделей он не отличает верный ответ от неверного (PR-AUC 0,029 при базовой доле 0,026, у z-score — 0,17).

### Модель
6. Готовые эмбеддинги не годятся (таблица в разделе 6), нужна дообученная ReID-модель: ID-loss плюс triplet или circle loss, PK-сэмплер с позитивами с других камер.
7. Начинать с CLIP-подобных или сильных supervised-бэкбонов. Сырой DINOv2 CLS кодирует ракурс и фон, а не машину.
8. Кадры одной серии считать одним видом при сэмплировании: остальные кадры почти копии.
9. Снизить вес пары камер 89/90 в сэмплере и отдельно проверять метрику на ней.
10. Бороться со смещением по камере: негативы с той же камеры, camera-wise BN или вычитание среднего эмбеддинга камеры (даже без обучения даёт +22–32% mAP).
11. Ракурс — главный источник ошибок: flip, crop, random erasing; сравнить вход 320×240 (под w/h ≈ 1,35) с 256×256; part- или attention-головы; потоковый re-ranking по галерее.
12. Ночь и низкое качество закрывать аугментациями яркости и цвета, отдельная ветка не нужна.
13. Следить за временем на одно ТС и FPS (`reid.benchmark`) и суммарным размером всех весов (≤ 2 ГБ). Баллы за скорость насыщаются на 40 мс и 100 FPS, поэтому быстрее этого не нужно — приоритет качеству.

## 5. Запрещено
- Использовать номерные знаки и любые их остатки: дисквалификация.
- Использовать порядок строк, соседство строк, `image_id` или md5 файлов как признак, фильтр или тай-брейк.
- Эксплуатировать продублированные кадры.
- Подавать `camera_id` или производные от него признаки в модель, включая id камер, выведенные по фону (точность 93%): организаторы запретили, на тесте их нет.
- Использовать на инференсе другие запросы: query expansion, кластеризацию запросов, re-ranking с соседями среди запросов.
- Оценивать модель без исключения совпадений с той же камеры: серии завышают метрику.

Самые трудные запросы:
- машина не видна в том же ракурсе на другой камере (mAP 0,02 против 0,07);

## 7. Код протокола (из ноутбука)

```python
import numpy as np


def make_pseudo_test(df, seed=0, n_vehicles=None):
    """Test recipe: gallery = one random frame per (vehicle, camera), query = the rest.
    df: train rows with vehicle_id and camera_id. Indices come back sorted -> shuffle before inference."""
    if n_vehicles:
        keep = np.random.default_rng(seed).choice(df.vehicle_id.unique(), n_vehicles, replace=False)
        df = df[df.vehicle_id.isin(keep)]
    gal = df.groupby(["vehicle_id", "camera_id"]).sample(1, random_state=seed).index
    return np.sort(df.index.difference(gal).to_numpy()), np.sort(gal.to_numpy())


def reid_eval(sim, q_pid, q_cam, g_pid, g_cam, chunk=1024, topk_junk=10):
    """Market-1501 protocol: gallery items with the same vehicle AND camera as the query are junk (ignored).
    sim: (n_query, n_gallery) similarity matrix; *_pid = vehicle ids, *_cam = camera ids."""
    ap, r1, r5, inp, junk10 = [], [], [], [], []
    for s in range(0, len(q_pid), chunk):
        S = sim[s: s + chunk]
        order = np.argsort(-S, axis=1)
        match = g_pid[order] == q_pid[s: s + chunk, None]
        junk = match & (g_cam[order] == q_cam[s: s + chunk, None])
        good, valid = match & ~junk, ~junk
        cv_, cg = np.cumsum(valid, 1), np.cumsum(good, 1)
        npos = good.sum(1)
        rows = np.arange(len(S))
        first = cv_[rows, good.argmax(1)]
        last = cv_[rows, good.shape[1] - 1 - good[:, ::-1].argmax(1)]
        ok = npos > 0
        ap.append((np.where(good, cg / np.maximum(cv_, 1), 0).sum(1) / np.maximum(npos, 1))[ok])
        r1.append(first[ok] <= 1)
        r5.append(first[ok] <= 5)
        inp.append((npos / last)[ok])
        junk10.append(junk[:, :topk_junk].sum(1)[ok])
    ap, r1, r5, inp, junk10 = map(np.concatenate, (ap, r1, r5, inp, junk10))
    return {"mAP": ap.mean(), "R1": r1.mean(), "R5": r5.mean(), "mINP": inp.mean(), "junk in top-10": junk10.mean()}, ap
```

## 8. Вопросы к организаторам
Отвечены 16.09.2026:
- `camera_id` из train — можно для PK-сэмплинга, обучения и валидации, нельзя как вход модели.
- Id камер, выведенные по фону, на инференсе — нельзя (производный от камеры признак).
- Кадр той же серии в топ-10 — выбрасывается до усечения и не занимает слот.

Отвечены 20.10.2026:
- В gallery закрытого теста нет кадров той же машины с той же камеры, что и запрос.
- Итог по отказу — не только 0,7·F1 + 0,3·TNR: при прочих равных лучше сбалансированное решение без резкого перекоса precision над recall. Порог можно менять, обосновав это валидацией; берётся лучшая версия по метрикам, до или после изменения.

Остаются открытыми до получения их `evaluate.py`:
- В `submission.csv` только 10 id: если один из них — кадр той же камеры, попадает ли на его место 11-й? Наш `reid_eval_top10` считает, что нет.
- Считается ли верхний кандидат в `candidates.csv` верным, если это кадр той же машины с той же камеры? Основной расчёт пропускает такие кадры, как в mAP@10; строгий вариант (`F1_strict`) считает их ошибкой.

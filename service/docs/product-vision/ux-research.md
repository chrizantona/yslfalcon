# Рабочее место визуального сопоставления автомобилей

Исследование продуктовой архитектуры и UX для «Фалькон Тех», 21 сентября 2026. Это проект целевого сервиса, а не утверждение, что перечисленные возможности уже реализованы. Основание: исходное ТЗ, разделы 1–13; ограничения текущего runtime взяты из предыдущего аудита. Ресурсные ограничения команды здесь не используются для сокращения концепции.

## Продуктовая идея

Сервис должен превращать обезличенный кадр в короткий, проверяемый список визуальных совпадений и сохранять весь контекст принятого решения. Его главная поверхность — рабочее место оператора: **увидеть исходный объект → найти → сопоставить → сохранить результат вместе с основаниями**. Сильное впечатление создают точность и завершённость этого цикла, включая убедительный отказ, повторяемость и лёгкую интеграцию.

Заказчик на публичном сайте описывает разработку и интеграцию городской видеоаналитики, сопровождение продукта, мониторинг и работу с городскими центрами обработки данных. **Вывод из этого профиля:** полезен автономный компонент существующей инфраструктуры, который легко подключить к её рабочим процессам. Это вывод, а не дополнительные условия конкурса. [Официальный сайт «Фалькон Тех»](https://st-falcon.ru/).

Рабочее название концепции: **FALCON ReID — визуальное сопоставление транспорта**. Подзаголовок объясняет действие без технических сокращений. Брендовые акценты — точность взгляда, рамка выделенного объекта, чистая геометрия. Официальный логотип заказчика и его утверждённые цвета потребуют брендбука; предложенная ниже палитра — самостоятельная концепция.

Основная сущность в продукте — **наблюдение автомобиля**: кадр, конкретный BBox, уникальный идентификатор наблюдения. Один кадр может содержать несколько наблюдений. Нельзя смешивать image_id и идентичность автомобиля; нельзя автоматически объединять похожие наблюдения в «досье машины» без проверенного основания.

## Пользовательский путь

**До:** оператор вручную открывает множество кадров, удерживает исходный автомобиль в памяти, сравнивает похожие кузова, переносит скриншоты в отдельный документ. ТЗ описывает высокую трудоёмкость такого сценария; конкретное число сэкономленных часов нельзя обещать без измерения.

**После:** оператор передаёт кадр и готовый BBox, видит точную вырезку, получает решение сервиса и ранжированный список, открывает 2–4 изображения рядом, отмечает результат своей проверки и скачивает карточку со всеми исходными данными. При следующем открытии карточка показывает тот же результат той же версии сервиса.

Измерять пользу предлагается на размеченной контрольной подборке: время до корректного решения; число просмотренных кадров; доля ошибочных подтверждений; доля завершённых задач; время до экспорта. Сравнивать ручной путь и сервис на одних условиях, не выдавая скорость нейросети за экономию времени оператора.

## Семь поверхностей интерфейса

### 1. Поиск: ежедневное рабочее место

Стартовый экран сразу предлагает действие. Никаких обзорных графиков перед загрузкой кадра. Если галерея готова, виден блок «Изображение + область автомобиля». Если нет — понятное пустое состояние с переходом к импорту для администратора и контактом ответственного для оператора.

На широком экране слева — исходный кадр, предоставленный BBox и вырезка. По центру — крупный выбранный кандидат. Справа — лента ранжированных кандидатов. Верхняя строка содержит галерею, её версию и доступность поиска; нижняя строка — действия «Сравнить», «Сохранить подборку», «Экспортировать». Источник остаётся закреплённым при просмотре списка.

Ввод: JPEG/PNG + x, y, w, h в пикселях исходного кадра; загрузка аннотации или выбор одной из переданных рамок. Числовые поля и графическая рамка синхронизированы. Мышь не обязательна: рамка редактируется и с клавиатуры. Исправление оператором создаёт новый запрос с признаком происхождения BBox; официальный пакетный запуск всегда использует выданную разметку без ручной коррекции.

До запуска показать именно crop, который попадёт в модель. Ошибки файла, координат и пустой области объясняются рядом с соответствующим полем. Если BBox выходит за границы, применяется единая документированная политика ядра; UI не должен молча показывать иной crop, чем API. Оригинал, исходные координаты и любые допустимые преобразования сохраняются.

Результаты не переупорядочиваются во время чтения. Состояния «В очереди», «Обработка», «Готово» отражают реальные события; проценты не имитируются. Время показывается как измеренная длительность этого запроса, с раздельными подробностями при раскрытии.

### 2. Сравнение: понять различия, не потеряв исходник

Режим сравнения занимает почти весь экран: исходный crop закреплён слева, справа 1–3 выбранных кандидата. Можно открыть полный кадр каждого наблюдения, изменить масштаб, вернуть «Вписать», синхронно менять масштаб при желании. Панорамирование не должно изображать геометрическое соответствие деталей разных ракурсов: синхронизация масштаба — инструмент просмотра, а не автоматическая регистрация изображений.

Ранг и идентификатор кандидата всегда видны; исходный порядок модели сохраняется даже после визуальной фильтрации. Кнопки оператора: «Подтверждаю визуальное соответствие», «Не соответствует», «Недостаточно данных». Эти отметки записываются отдельно от ответа модели, не превращаются автоматически в ground truth и не запускают онлайн-дообучение.

При почти одинаковых автомобилях пользователь может сохранить несколько кандидатов на проверку. Нельзя показывать «тот же автомобиль доказан» только потому, что кандидат выше остальных. Интерфейс поддерживает неопределённость как завершённый рабочий результат.

### 3. Карточка результата: контекст, которым можно делиться

Это постоянная страница конкретного запуска: оригинал, BBox, crop, результаты, модельное решение и отдельная оценка оператора, выбранная галерея, версия модели и правила отказа. У страницы стабильная ссылка в пределах установки; скачиваемый пакет можно открыть вне сервиса.

Экспорт для человека: PDF/HTML-карточка и изображения. Экспорт для интегратора: JSON/CSV с исходными идентификаторами, порядком, численными оценками и версиями. Комплект содержит manifest и хеши файлов для проверки целостности. Хеш не следует выдавать за электронную подпись или юридически удостоверенное доказательство.

Текст карточки: «Кандидат предложен моделью; визуально проверен оператором / не проверен / данных недостаточно». Время в карточке — время запроса и проверки; время съёмки отсутствует, если его не было во входных данных. Координаты и камера не выдумываются.

Отдельный экспорт конкурса строит submission.csv, embeddings.npy, candidates.csv по официальному контракту. Продуктовый отчёт не заменяет эти артефакты. Порядок, значения и решение должны совпадать с исходным сохранённым результатом, без нового незаметного поиска.

Практический ориентир: в XProtect результаты поиска, просмотр выбранного материала и детали представлены в одном рабочем пространстве; документация описывает действия над найденными материалами. Нам полезна эта связка «результат → проверка → действие», а не камера/время как поля, которых в задаче нет. [Milestone: Search workspace и точки интеграции](https://doc.developer.milestonesys.com/mipsdk/gettingstarted/intro_searchagent.html).

### 4. Галереи: понятная готовность данных

Администратор видит название, размер, активную версию, модель совместимого эмбеддинга, статус индекса и статус калибровки. Создание галереи — мастер из трёх шагов: загрузить кадры и CSV; проверить; активировать готовый snapshot.

Предпросмотр импорта показывает: принято наблюдений; повреждённые файлы; отсутствующие image_id; некорректные BBox; дубликаты; сколько разных рамок относится к одному кадру. Ошибки можно скачать одним CSV. Нельзя молча импортировать 93% файла и объявить весь набор готовым.

Состояния: черновик → проверка → построение признаков → индексация → готова к активации → активна. Неуспешное обновление не ломает предыдущую активную версию. Текущие запросы заканчиваются на snapshot, с которым начались.

Состав и размер галереи влияют на применимость правила отказа. «Индекс готов» и «решение о совпадении откалибровано» — две разные проверки. Маленькая демогалерея не должна искусственно порождать отказы, если используемый score математически не может достичь порога.

### 5. Качество и разбор ошибок: предметная панель для ML-лида и жюри

Показываются паспорт конкретной версии и воспроизводимый протокол: используемая выборка, размер галереи, определение метрик, выбранный порог, фактические метрики при этом пороге, дата прогона, версия scorer. Dev-результаты явно подписаны как dev; метрики закрытого теста появляются только после получения от организаторов.

Главный вид — не россыпь графиков, а четыре группы примеров: корректное предложение; корректный отказ; ложное предложение; пропущенное совпадение. По каждому случаю доступны исходные кадры, ranks, score, ошибка и наблюдаемая причина либо «причина не установлена». Разрезы по ракурсу/качеству/перекрытию допустимы лишь при наличии разметки или явно описанного способа измерения; камера не выводится из имени файла.

График выбора порога показывает trade-off F1/TNR и выделенную точку поставки. Изменение ползунка создаёт песочничный расчёт и не меняет рабочий порог. Для сравнения двух model bundles можно запустить один замороженный набор, увидеть изменения порядка и решения и открыть самые сильные расхождения. Это дополнительная возможность целевого сервиса, а не обязательный экран оператора.

### 6. Интеграция: портал, который снимает вопросы у инженера заказчика

Локально доступные OpenAPI, примеры входного файла и BBox, интерактивный пример запроса, результат с объяснением полей, таблица статусов ошибок, контракты пакетного импорта и экспорта. Все примеры работают без внешнего CDN или обращения в облако.

Главное демонстрационное действие: взять уже выполненный поиск из интерфейса, открыть соответствующий API-запрос и получить те же candidate IDs, порядок, решение и версии. У браузера и API один контракт. Показать correlation ID, повтор запроса без дубля задания и ссылку на исходный объект во внешней системе, только если интегратор её действительно передал.

Названия методов ориентированы на наблюдения, галереи и поиски; логины камер, RTSP, OCR и трекинг не появляются. Модуль можно включить в существующую систему как отдельный сервис. Возможность расширять централизованное поисковое рабочее место через внешние search agents существует, например, в официальном SDK Milestone; это пример интеграционного паттерна, не утверждение о готовой совместимости с конкретным VMS. [Milestone MIP SDK](https://doc.developer.milestonesys.com/mipsdk/gettingstarted/intro_searchagent.html).

### 7. Состояние сервиса: уверенность в эксплуатации

Для администратора: доступность API и inference, активный model bundle, готовность галерей, длина очереди, объём хранилища, ошибки импорта, текущие задания и реальные задержки. «Процесс работает» не равно «поиск готов». Показаны последние успешные проверки; диагностический пакет не включает пользовательские изображения по умолчанию.

Для оператора достаточно компактной строки готовности. Технические подробности раскрываются при проблеме или по запросу. При сбое поисковая форма и загруженный crop сохраняются; повтор не требует загрузить всё заново. Отмена, перезапуск и повтор задания имеют явную семантику, а перегрузка не маскируется модельным отказом.

## Честные состояния и уверенность

Модельное решение, техническое выполнение и оценка оператора должны храниться отдельно. Это предотвращает превращение любой проблемы в «совпадений нет».

| Ситуация | Что видит оператор | Что означает | Что делать |
|---|---|---|---|
| Правило предложения пройдено | «Предложен кандидат» | Сработало проверенное правило модели на совместимой галерее | Сравнить исходные изображения |
| Корректный модельный отказ | «Уверенное совпадение не найдено» | Поиск выполнен, правило отказа применено, принятых кандидатов нет | Сохранить отказ или открыть диагностический список |
| Неоднозначность | «Требуется визуальная проверка» / «Недостаточно данных» | Отдельное состояние проверки человеком; либо валидированный флаг review, если его специально разработали | Сравнить несколько кандидатов, оставить отметку |
| Калибровка неприменима | «Для этой галереи решение о совпадении недоступно» | Ранжирование может работать, но проверенного основания принять/отказать нет | Администратор выбирает совместимую конфигурацию |
| Техническая ошибка | «Поиск не выполнен» + конкретная причина | Модельного решения нет | Исправить входные данные, повторить или обратиться по request_id |

Неоднозначность сама по себе не становится третьим классом официального scorer. При действующей конкурсной политике экспорт остаётся тем, что требует ТЗ; отметка оператора и diagnostic shortlist не изменяют accepted_candidates. Если добавляется отдельная автоматическая review-policy, её проверяют и версионируют отдельно.

**Query-level confidence** отвечает на вопрос: достаточно ли уверенности у системы, чтобы предложить результат для этого запроса в этой галерее. Это один показатель для всего запроса. **Pair score** описывает сходство конкретных двух изображений либо значение их реранжирования. Первое нельзя скопировать на каждую карточку и подписать вероятностью совпадения пары.

Для текущего пути аудита следует показывать: ранг; статус прохождения порога запроса; по раскрытию — исходный cosine пары, score реранжирования с корректным названием, query-confidence и порог. Если итоговый rank_score получен перестановкой исходных значений, он не подписывается cosine соответствующей пары. Подпись «97%» допустима только для отдельно проверенной вероятностной калибровки соответствующего события и применимой выборки. Размер полоски «похожести» тоже не должен притворяться вероятностью.

Если принятие сейчас валидировано только для верхнего кандидата, именно он является принятой рекомендацией; остальные — ранжированные варианты для просмотра. Полноценный список индивидуально принятых кандидатов требует определения и проверки правила принятия каждой пары. Нельзя объявить весь top-10 уверенными совпадениями из-за одного хорошего query score.

При отказе основной список принятых результатов пуст. Ниже можно раскрыть «Наиболее похожие изображения — порог не пройден»; диагностические элементы имеют нейтральное оформление и не попадают в accepted_candidates. Фраза «машины нет в городе/архиве» недопустима: модель установила лишь отсутствие достаточной уверенности в выбранной галерее.

## Объяснение результата по запросу

В карточке сравнения действие называется «Показать области, влияющие на оценку». Сначала видны настоящие изображения, затем пользователь включает полупрозрачную карту для выбранной пары. Рядом указаны объясняемый score, метод и ограничение. Для ViT/reranker нужен метод, применимый к фактической архитектуре и целевой скалярной оценке; нельзя прикрепить обычную карту классификатора training IDs к открытому поиску и назвать её объяснением финального решения.

Сильный вариант — считать attribution для реального pair score выбранного кандидата; отдельно, при необходимости, объяснять этап encoder и reranker. Если показана лишь attention map encoder, подпись прямо говорит «распределение внимания encoder», без утверждения, что это причина принятия или отказа. Разность scores при маскировании областей можно использовать как диагностический метод, проверив ограничения искусственного вмешательства во вход.

Объяснения считаются отдельной задачей после результата, кэшируются по полному model bundle, входам пары, методу и параметрам объяснения. Основной объект объяснения — score пары; объяснение места дополнительно закрепляет gallery snapshot, search profile, окно и оценки других кандидатов. Объяснения не увеличивают обязательную задержку поиска. До публикации проверяются хотя бы чувствительность к параметрам модели, разные пары/ракурсы и характерные ошибки. Исследование saliency показывает, почему красивая карта сама по себе не доказывает связь с обученной моделью. [Adebayo et al., Sanity Checks for Saliency Maps](https://proceedings.neurips.cc/paper/2018/hash/294a8ed24b1ad22ec2e7efea049b8737-Abstract.html). Grad-CAM исходно строит грубую локализацию для выбранной целевой величины; метод нужно адаптировать к конкретной архитектуре и не выдавать за доказательство идентичности. [Selvaraju et al., Grad-CAM](https://openaccess.thecvf.com/content_ICCV_2017/papers/Selvaraju_Grad-CAM_Visual_Explanations_ICCV_2017_paper.pdf).

Не генерировать из heatmap неподтверждённые объяснения «совпали уникальная царапина и наклейка». Такие признаки можно описать как наблюдение оператора с его авторством. Нельзя дорисовывать детали автомобиля, улучшать номер или подменять исходный crop генеративной реконструкцией.

## Десять отличительных возможностей и их основание

«Обязательное» ниже означает прямое требование ТЗ; «арбитр» — раздел 10, учитываемый только при равенстве основных метрик; «дополнение» — наша продуктовая рекомендация, не обещание дополнительных баллов.

| Возможность | Задача пользователя | Связь с ТЗ | Сильная реализация |
|---|---|---|---|
| Проверяемый ввод кадра и BBox | Быть уверенным, что ищется нужный объект | **Обязательное**, §§3–5 | Оригинал и точный crop рядом; явная валидация; отдельный observation_id для каждой рамки |
| Рабочее место сравнения | Быстро отличить похожие автомобили | **Арбитр**: удобное демо, §10 | Закреплённый запрос, 2–4 изображения, масштаб, полный кадр, быстрые клавиши |
| Полноценный результат отказа | Не принять похожую машину за искомую | **Обязательное**, §§3–4, 9 | Отказ имеет собственную карточку; похожие изображения не выдаются за принятые |
| Паспорт решения | Повторить и проверить полученный вывод | **Дополнение**, усиливает воспроизводимость §§6, 12 | Галерея, модель, порог, исходники и результаты зафиксированы одной записью |
| Экспорт, сохраняющий контекст | Передать результат коллегам и системе | **Арбитр**, §10; конкурсные файлы обязательны по §8 | Читаемая карточка + JSON/CSV + manifest; отдельный официальный export |

| Галерея с безопасной активацией | Обновлять данные без потери текущего поиска | Хранение **обязательно**, §6; versioning — **дополнение** | Валидированный snapshot, совместимость модели/калибровки, атомарная активация |

## Визуальная система

Предлагается спокойная промышленная эстетика: графитовая оболочка, нейтральные поверхности для кадров, светлый текст, один фиолетовый акцент для активного действия и рамки запроса. Это проектная палитра, а не установленный фирменный стиль заказчика. Светлая тема для дневной работы — равноправный режим. Фотографии остаются главным содержимым, а не декоративным фоном.

Оболочка компактная: слева текстовая навигация с иконками; оператор по умолчанию видит «Поиск», «Подборки», «История», а администратор — дополнительные разделы. Размер кадров можно менять без изменения порядка. На большом экране — три колонки; на ноутбуке — закреплённый исходник и результат; на узком экране — последовательные панели с доступным возвратом к исходнику. Настоящее сравнение ориентировано прежде всего на рабочий стол.

Предлагаемые проектные размеры: базовый текст 15–16 px; идентификаторы и score — табличные цифры; основные действия 40–44 px по высоте. Минимум WCAG 2.2 AA для цели указателя — 24×24 CSS px с определёнными исключениями; выбираем более удобные основные элементы. [W3C: Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Текстовая контрастность минимум 4.5:1 для обычного текста и 3:1 для крупного. Статус всегда включает текст и значок; цвет не является единственным каналом. Клавиатурный focus заметен, порядок перехода логичен, горячие клавиши не перехватывают ввод в полях. Обновление статуса поиска доступно assistive technologies без переноса focus. [W3C: Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), [Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

Анимация служит ориентации: открытие сравнения, завершение загрузки, смена состояния. Она не изображает «сканирование автомобиля» или выдуманную работу модели. Статус отказа спокойный, нейтральный; красный сохраняется для ошибки выполнения, чтобы нормальный продуктовый ответ не выглядел поломкой. Скелетоны повторяют реальную структуру, а не превращают ожидание в бессрочное шоу.

## Демонстрация на 7 минут

Демо строится на размеченной разрешённой подборке и репрезентативной галерее; подготовленные примеры честно названы демонстрационными. Порог зафиксирован заранее. Данные для выбора порога и демонстрационный рассказ не смешиваются с закрытым тестом. На экране нет настоящих или выдуманных camera_id, времени съёмки, карт и маршрутов.

| Время | Действие на экране | Что должно стать очевидным |
|---|---|---|
| 0:00–0:40 | Кадр с нечитабельным/анонимизированным номером и готовым BBox. Оператор проверяет crop | Решается ровно задача заказчика: визуальное сопоставление без номера |
| 0:40–1:40 | Поиск по подготовленной галерее, выбор верхнего кандидата в другом ракурсе, открытие пары | Результат легко проверить глазами, источник не теряется |
| 1:40–2:30 | Открыть похожий, но другой автомобиль; сравнить 2–3 кандидата; отметить проверку | Сервис помогает работать со сложными случаями, отделяет модель от человека |
| 2:30–3:20 | Запрос без совпадения в галерее; реальный отказ; раскрыть диагностический список | «Не знаю» — нормальный завершённый ответ; ближайший сосед не притворяется совпадением |
| 3:20–4:00 | Для выбранной пары включить проверенную карту влияния, показать исходник и подпись метода | Интерпретируемость конкретна и не заменяет визуальную проверку |
| 4:00–4:40 | Экспортировать карточку, открыть файл, показать версии и оригиналы | Результат покидает демо без потери контекста |
| 4:40–5:30 | Открыть соответствующий API-запрос и тот же ответ; показать локальную спецификацию | Компонент можно встроить в систему заказчика |
| 5:30–6:15 | Показать версию галереи, реальный отчёт ANN на ~10^6 и measured recall/latency, если реализовано | Масштабируемость имеет проверяемое основание; synthetic scale помечен отдельно |
| 6:15–7:00 | Открыть один честный провал и паспорт порога; завершить схемой автономной установки | Команда понимает ограничения и умеет передать воспроизводимый продукт |

Все динамические числа берутся из настоящих запусков. Если показан заранее сохранённый прогон, рядом это написано. Для ANN отдельно показываются число объектов, источник и состав данных, аппаратная конфигурация, режим поиска и сравнение с exact. Дубликаты не превращают маленькую реальную галерею в доказательство качества на миллионе автомобилей.

## Архитектурные следствия UX

1. Результат поиска — сохраняемая неизменяемая сущность, а не временный ответ браузеру. Она ссылается на конкретный model bundle, gallery snapshot и policy version.
2. Ответ ядра разделяет технический статус, модельное решение, accepted candidates, ranked/diagnostic candidates, score semantics и timing. UI не восстанавливает решение из визуального цвета карточки.
3. Операторская оценка — отдельная запись с авторством и временем. Она не перезаписывает модельный результат и не попадает в обучение автоматически.
4. Отчёт строится из сохранённого результата; повторный поиск создаёт новую версию сравнения. Пересборка индекса не меняет прошлые карточки.
5. Объяснение — отдельное версионированное задание с ясной целевой величиной и ограничениями; его сбой не отменяет выполненный поиск.
6. Импорт галереи, построение индекса и его активация — раздельные переходы состояния; переключение не разрывает текущие задачи.
7. Калибровка имеет собственный контракт применимости. Готовность индекса не даёт права автоматически применить любой threshold.
8. Внешняя система передаёт изображение и BBox через тот же контракт, что браузер. Дополнительные внешние метаданные при наличии хранятся как контекст, но в конкурсном профиле не становятся признаками ReID.

Концепция не требует детекции, OCR, tracking, карт, генеративного чата или выдуманных потоков камер. Её отличие — завершённость главной задачи: каждое действие оператора имеет понятный следующий шаг, каждое решение сервиса можно проверить, сохранить и воспроизвести.

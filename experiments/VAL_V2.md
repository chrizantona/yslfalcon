# Переход на протокол val_v2 и пересчёт экспериментов

Дата: 16.09.2026. Причина — ответы организаторов: как считаются основная метрика, режим отказа и скорость, и какие приёмы разрешены.

## Что изменилось в протоколе
| | val_v1 | val_v2 |
|---|---|---|
| Главная метрика | полный mAP по всей галерее | **mAP@10** по топ-10, как в `submission.csv`: кадры той же машины с той же камеры выкидываются из списка, AP делится на min(n_pos, 10), запросы без пары исключаются |
| Справочно | — | полный mAP и mINP по всей галерее |
| Отказ: когда ответ верный | верен любой принятый кандидат из топ-10 | решает только **верхний** кандидат (кадр той же камеры пропускается); строгий вариант `F1_strict` считает его ошибкой |
| Отказ: подсчёт | recall = TP / все запросы с парой | как у организаторов: TP, FP (неверный ответ или ответ без пары), FN (отказ при паре), TN; F1 = 2TP / (2TP + FP + FN) |
| Запросы без пары | ~30% (убраны 30% машин) | **~20% запросов** (машины убираются целиком, пока не наберётся 20%) |
| Выбор порога | лучший F1 при TNR ≥ 0,5 | максимум **0,7·F1 + 0,3·TNR** — формула баллов организаторов |
| Отказ в `candidates.csv` | строка с пустым `gallery_id` | **строк нет** |
| Потоковость | не проверялась | другие запросы использовать нельзя |

Фолды и псевдо-тест (`fold{k}_query.csv`, `fold{k}_gallery.csv`, `folds.csv`) скопированы из `val_v1` без изменений: байт в байт, проверено `cmp`. Поэтому все эксперименты пересчитаны по сохранённым эмбеддингам фолда 0 без переобучения (`reid.recompute`). Результаты — в `artifacts/<EXP>/val_v2/`, сводка — в `experiments/registry_val_v2.csv`.

## Режим отказа на val_v2
| | EXP-003 | EXP-010 | EXP-016 |
|---|---|---|---|
| баллы 0,7·F1 + 0,3·TNR | 0,829 ± 0,007 | 0,871 ± 0,006 | 0,872 |
| F1 | 0,770 | 0,829 | 0,832 |
| TNR | 0,965 | 0,968 | 0,965 |
| доля ответов | 0,738 | 0,745 | 0,750 |
| порог (z-score top-1) | 5,39 | 6,20 | 6,13 |
| `F1_strict` | 0,020 | 0,032 | 0,036 |

- Формула баллов тянет порог вверх: TNR около 0,97, при этом часть запросов с парой получает отказ (ответов 75% при 80% запросов с парой).
- **Главный риск — `F1_strict`.** Почти у каждого запроса первым идёт кадр той же машины с той же камеры — поэтому `F1_strict` близок к нулю. Если организаторы засчитают такой верхний кандидат как ошибку, F1 упадёт до 0,02–0,04, и режиму отказа понадобится своя логика: например, не выводить первым почти идентичный кадр. Ответ даст эталонный `evaluate.py`.
